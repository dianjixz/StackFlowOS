# Agent 需要的不是更好的软件，是一个能住的系统

> 对 README 里那段想法的展开。原始判断保留在 `README.md`，这里只做三件事：
> 把模糊的直觉拆成可证伪的命题、指出一条因果链的断裂处、给出可执行的路线。
>
> 文中标 **[已核]** 的是读了源码/文档确认的，标 **[推断]** 的是从架构推出来但没实测的。

---

## 0. 一句话

README 里真正在说的，不是"做个更好的 Agent 产品"，而是：

**Agent 现在缺的不是能力，是"操作系统的位置"。**

它一直以"被人类打开的应用"的身份存在，而不是"住在机器里的进程"。
这两者的差别不在 UI，在**权限、生命周期和状态归属**。

## 2. Cordis 的边界不在语言，在"作用域是进程内的对象树"

README 说"Cordis 无法多设备联动执行"，这个观察是对的，但归因容易走偏——
容易以为是 TypeScript、是 Node、是性能。都不是。

**[已核]** 读 Cordis 的实现，三处决定了它只能单进程：

1. **`Context` 是 `new Proxy(this, ReflectService.handler)`**。
   `ctx.tools`、`ctx.llm` 这种"看起来像属性"的服务，底层是内存里的服务解析器。
   属性读取 = 一次本地查表，没有"远端"这个分支。

2. **`Fiber` 的 disposables 是进程内的闭包**。
   插件卸载时按逆序调用 disposer——这个逆序回收之所以可靠，全靠它们同在一个进程里。

3. **事件是进程内 `EventsService`**。
   `waterfall` 的"调用 `next()` 才继续"语义，本质是同步调用栈上的环绕中间件。
   跨网络的 `next()` 不是中间件，是分布式事务。

所以结论要改写：

> Cordis 缺的不是传输层，是 **`Context` 没有远程实现**。
> 它的"作用域"这个概念，物理上钉死在单进程里。

这个改写很重要，因为它把二选一变成了分工：

**Cordis 当语义层，StackFlow 当传输层。它们不冲突。**

而且这条缝是可以补的——第 4 节给三层结构，第 6 节给最小验证。

## 3. StackFlow 作为传输底座：已经有什么，还缺什么

本机 `/home/nihao/w2T/axera/StackFlow` 是真实工程（M5Stack，MIT，AX630C/AX650N）。
以下全部读源码核对过，不是从 README 抄的。

### 3.1 它天生就是"分布式"的形状 [已核]

| 已有能力 | 实现位置 | 对 OS 的意义 |
|---|---|---|
| 统一寻址 `work_id` = `<unit>.<n>` | `remote_server.cpp:43` | 进程实例有稳定名字，等价于 PID |
| 端口池 5010–5555 自动分配 | `main.cpp:61-62` | 资源分配，等价于 fd 表 |
| RPC 通道（REQ/REP） | `pzmq.hpp` | 控制面 |
| 数据通道（PUB/SUB） | `StackFlow.cpp` | 数据面 |
| 装配动作 `setup/link/unlink/exit` | 七个基础 action | **等价于 fork/pipe/close/wait** |
| 地址格式是运行时 KV | `main.cpp:52-53` | 不是编译期常量 → 见下 |

最后一条是整个方案的支点：

```cpp
key_sql["config_zmq_s_format"] = std::string("ipc:///tmp/llm/%i.sock");
key_sql["config_zmq_c_format"] = std::string("ipc:///tmp/llm/%i.sock");
```

`%i` 是端口号占位。**这意味着把它改成 `tcp://<host>:%i`，数据面就具备跨设备的形态**——不需要改编译产物。
**[推断]** 没实测，这是第 6 节第 0 步要验证的第一件事。

### 3.2 五处硬伤，按阻塞顺序排

做"多设备 OS"必须先知道哪里会流血。

**① RPC 地址头硬编码，sys 的 RPC 出不了本机** [已核]
```cpp
std::string rpc_url_head_ = "ipc:///tmp/rpc.";   // pzmq.hpp:93，私有成员
```
只有服务名里含 `://` 时才会 `clear()` 绕过（`pzmq.hpp:121`）。
而 `llm-sys` 注册的服务名是裸的 `sys`，所以 **sys 的 RPC 永远是 unix socket**。
数据面能跨设备、控制面不能——这是第一块必须动的代码。**这是全案第一拦路石。**

**② 端口池是单机本地的** [已核]
`port_list[]` + `port_list_start` 是进程内数组；`sys_release_unit` 用 `sscanf(output_url, "%i")` 反解端口，
隐含假设"端口号 = 池内偏移"（`remote_server.cpp:128-133`）。
两台设备各自从 5010 起分配 → 跨设备寻址会撞车，而且 `port_list[port - start]` 有越界风险。

**③ 没有身份、没有租约、没有失败域** [已核]
外部 TCP 10001 上任何客户端都能发 `bashexec`（root bash）。
没有 token、没有 capability、没有"这个 work_id 被谁占用到什么时候"。
对人是便利，对 AI 是**不可授权**——你不敢让一个自主 Agent 拿到这个端口。

**④ PUB/SUB 无背压、无 ack** [已核]
`link` 只是订阅，慢消费者丢帧（ZMQ 默认 HWM 行为），上游不知道下游掉队。
跨设备后网络抖动会把"丢帧"变成常态。

**⑤ `remote_server.cpp:83` 疑似笔误** [已核]
```cpp
std::string zmq_format = zmq_c_format;
if (zmq_s_format.find("sock") != std::string::npos) {   // ← 应为 zmq_c_format
```
因为 s/c 默认值相同所以从未暴露；但一旦只改 `c_format` 做实验，这里会错位。

## 4. 那么真正的系统是三层的，缺口在第三层

```
┌──────────────────────────────────────────────────────────┐
│  L2  编排层  ← 这才是"OS"，也是 README 里没说到的部分      │
│      能力目录 · 任务租约 · 失败域 · 跨设备上下文流          │
│      状态：谁在占什么、占多久、挂了归谁                     │
├──────────────────────────────────────────────────────────┤
│  L1  语义层  ← 继承 Cordis 的正确部分                      │
│      可逆副作用(effect/disposer) · 服务注入(inject)        │
│      类型化事件(waterfall/serial) · 无特权内核             │
│      状态：进程内的插件树                                  │
├──────────────────────────────────────────────────────────┤
│  L0  传输层  ← StackFlow 已经做完了 80%                     │
│      work_id 寻址 · 端口池 · RPC + PUB/SUB · setup/link     │
│      状态：socket 与进程                                   │
└──────────────────────────────────────────────────────────┘
```

**关键判断：缺的是 L2，不是 L0 也不是 L1。**

L0 已经有人替你写了十年（ZMQ + StackFlow 的装配模型）。
L1 的思想 dsh 已经验证过了（MIT，可抄）。
L2 是空白——市面上所有 Agent 框架在这一层都是空的，因为它们假设"一个进程 = 一个 Agent"。

### 4.1 L2 的四个组件

**① 能力目录 Capability Registry**
不是"哪台机器装了什么模型"，而是"**当前能承诺什么**"。
要能回答：这台设备现在有没有空闲的 NPU、显存够不够 1.5B、跑 qwen 时首 token 延迟多少、
上一个任务什么时候结束。
设计哲学抄 `/proc` 和 `/sys`：**可枚举、反映真实状态、不许撒谎**。
现有的 `taskinfo` 只返回 work_id 列表，信息量不够做调度。

**② 任务租约 Lease** ← 最被低估的一块
AI 发起的不该是"调用"，而是"**占用**"。
```
lease = { resource: work_id, holder: agent_id,
          ttl: 300s, renewable: true, preemptible: false }
```
为什么这是"自主"的物理前提：**没有租约，AI 不敢接长任务**。
因为随时可能被别人的请求挤掉，也没法保证"我占着这块 NPU 直到算完"。
人之所以能干活，是因为"我坐下来这台电脑就是我的"——租约就是这句话的机器版。

**③ 失败域 Failure Domain**
一个单元挂了：谁重启、谁降级、谁换设备、谁的上下文作废。
这一层没有，多设备只会把单点故障放大成雪崩。

**④ 跨设备上下文流**
会话日志不是 chat history，是 **append-only 事件流**。
**[已核]** dsh 这点做对了：`SessionEvent` 追加日志 + `session/event` 广播，
resume / fork / replay 共用同一条流。跨设备要续的是**这条流的位置**，不是几句对话。

## 5. 更锋利的一句：AI 管家的瓶颈不是智能，是授权

README 说"想要像贾维斯那样的 AI 管家，充分发挥 AI 自主独立能力，就应该给 AI 一个适合的环境"。
这句我完全同意，但想补一刀——

**"适合的环境"不等于"能力更强的环境"，而是"后果可承担的环境"。**

人可以随手改自己的系统，不是因为人更强，是因为**人承担后果**。
AI 要能动，需要让后果变得可承担的结构。三个必要条件，缺一不可：

| 条件 | 对应机制 | 谁已经做对了 |
|---|---|---|
| **可观测**：AI 读到的必须是真实状态，不是别人嚼过的摘要 | 能力目录 / 不做假的状态源 | 没有（所有框架都在喂摘要） |
| **可试错**：动作可逆，失败有边界 | effect / disposer / 事务式装配 | Cordis 的 `ctx.effect()` |
| **可回滚**：跨设备的动作也能撤回 | 租约到期释放 + `exit` 补偿 | 没有 |

所以 Cordis 那套"每个注册都配一个 disposer"不是工程洁癖，**它是"让 AI 敢动手"的安全带**。
这也是为什么 L1 必须继承 Cordis 而不是重写——这套可逆性是被 4000+ 插件验证过的。

README 里"世界模型是一种方式，但真正的还是需要一个系统"——可以再推一步：
**世界模型解决"AI 怎么想"，系统解决"AI 怎么被允许动"。前者是认知问题，后者是权限问题。
贾维斯卡住的地方，从来不是它不够聪明。**

## 6. pynng 机群算不算？

直接回答：**算传输层的一种实现，但不算系统**；而且和 StackFlow 是**替代关系，不能叠加**。

| | StackFlow / libzmq | pynng / NNG |
|---|---|---|
| 抽象层级 | message pattern（pub/sub/req/rep/pipeline） | 同一层，nanomsg 的演进版 |
| wire 协议 | ZMTP | SP 协议 |
| 互操作 | **不能直连**。除非自己写 bridge，否则一个用 libzmq 一个用 pynng 是两座孤岛 | |
| 现成资产 | 设备上已经在跑，有 work_id/端口池/装配动作 | Python 侧写起来快 |
| 给你的东西 | 消息模式 | 消息模式 |
| **都不给** | 身份、目录、租约、失败域 | 同左 |

所以 README 里"pynng 机群算不算"的答案是：
**它是 L0 的另一个候选实现，不是 L2 的答案。**
选它唯一的好理由是"L2 用 Python 写、想少一层 ctypes"——但那也得写 bridge，收益不大。

**协议要先定，但不是从协议规范开始。** 见下。

## 7. 从协议开始还是从基础累进？——从"最窄的一条跨设备链路"开始

设计协议最容易变成空转：写出一份漂亮的 IDL，然后发现没人实现。
正确顺序是**让协议从能跑的东西里长出来**，每一步都有明确的证伪点。

### 第 0 步：验证地址真的可配置（半天，可证伪）
```bash
# 单机上把数据面从 ipc 改成 tcp，跑通 AUDIO → KWS
# 只改 config_zmq_s_format / config_zmq_c_format
```
**证伪点**：如果 `%i` 只能被 `sscanf` 按 ipc 路径反解、tcp 形式下端口池对不上（硬伤②），
那么"地址可配置"就是假象，后面全要重来。
**这一步的价值：花半天排掉一个可能让整个方案作废的假设。**

### 第 1 步：两台设备跑通一条流（2–3 天）
设备 A 只跑 KWS，设备 B 只跑 ASR，用 tcp 地址 `link`。
**证伪点**：延迟、丢帧率。如果 tcp 下 PUB/SUB 抖动导致端到端不可用，
说明 L0 需要先补背压（硬伤④），而不是急着上 L1。

### 第 2 步：把 RPC 拉出本机（第一块真代码）
改 `pzmq.hpp` 的 `rpc_url_head_`：要么做成可注入的成员，要么让 `sys` 注册成 `tcp://...`。
**这是全案唯一的"必须 fork"点**，也是"能不能不改上游"的分水岭。

### 第 3 步：能力目录（只读，先不做调度）
一个聚合服务，把各设备的 `taskinfo` + `hwinfo` 收上来，给一个只读视图。
**先做只读**，因为可观测是三个条件里最便宜、收益最大的，而且它不破坏任何东西。

### 第 4 步：租约（第一个"新概念"）
最小实现：`setup` 时带 `ttl`，到期自动 `exit`。只加字段，不加协议。

### 第 5 步：才轮到 Cordis 语义
把 L1 的可逆插件树套到 L2 的目录/租约上。
**放最后**，因为它依赖前三步的真实形状；先做就会设计出一个漂亮的空壳。

### 那条"窄契约"
L0 和 L2 之间只需要一个东西：`work_id` + `action` + `object`/`data`。
**这条契约稳住，下面换 ZMQ→NNG、上面换 Cordis→别的，都不影响。**
协议的价值不在完备，在于**窄到可以十年不换**。

## 8. 命名与边界

**StackFlowOS ≠ StackFlow。**

| | StackFlow | StackFlowOS |
|---|---|---|
| 是什么 | 设备侧运行时（单机） | 集群/编排层（多机） |
| 归属 | M5Stack 产品线，MIT | 新的东西，可独立演进 |
| 改动 | 尽量不改；只在第 2 步动一次 | 全部新建 |
| 依赖方向 | 不知道上面有 OS | 依赖 StackFlow 的窄契约 |

这条边界不划清，两个项目会互相污染：
一旦把编排逻辑写进 `llm-sys`，单机运行时就被绑死在你的集群假设上，M5Stack 没法维护。

## 9. 我没验证的部分（诚实清单）

1. **tcp 形式的 `%i` 是否真的能跑通** —— 只读代码判断"应该可以"，没实测。第 0 步就是为了这个。
2. **dsh 是否已有跨设备能力** —— 我核了插件架构（sandbox provider 是插件，理论上可指向远端），
   但"一个 agent loop 编排多台设备"在文档里没见到。**这是"文档未见"，不是"确定没有"。**
3. **PUB/SUB 跨设备后的实际抖动** —— 取决于网络，必须实测。
4. **`remote_server.cpp:83` 是不是真 bug** —— 是笔误的形状，但因为默认值相同从未触发，可能是有意为之（`zmq_c_format` 从未被独立使用）。改之前先问。
5. **L2 的复杂度** —— 能力目录 + 租约 + 失败域是三个独立子系统，不是一次能做完的。
   路线图把租约排在第 4 步，是因为它最小可用版本只需要一个字段。

## 10. 一句话收尾

README 里那句"如果从 StackFlow 开始，也许是一个很好的选择"——是对的，但理由要说准：

**不是因为 StackFlow 更完整，而是因为它已经解决了 L0（寻址和装配），
而这恰好是 Cordis 缺的那一块的地基。**

真正要新建的是 L2。L2 里最该先做的是**租约**，
因为"AI 敢不敢自主干活"，物理上取决于"它能不能确定自己还占着资源"。
